# Review: faithful JSON save/restore ledger plan

**Status:** review of a porting plan for an **unadopted** take. Not
playbook, constitution, or runbook. Loop agents must not consume this
as a work list.

**Date:** 2026-08-30.
**Reviewer:** Claude, at operator request.
**Plan under review:** `.cursor/plans/save_restore_ledger_91af84ce.plan.md`
("Save Restore Ledger", Grok).
**Operator intent (from the Cursor thread):** *"porting save & restore
faithfully now so that we could easily rely on that to compare custom
recorded sessions based on autogenerated saves"*, and *"I'd really like
to do this in one big take."*
**Checked against tree:** `605f0f2e` = D-1693, suite 44/44.

---

## Verdict

**APPROVE THE THESIS — REWORK THE MECHANISM.** The goal is right and
the C reading is mostly right, but the plan as written would produce a
**wrong** oracle, not merely an incomplete one, in five places.

The single largest problem is architectural: **the plan does not model
where C relinks `o_id` → object.** C relinks *inside every `getlev`*
(`restore.c:1299–1300`), against a `find_oid` (`shk.c:2777–2804`) whose
search space is *only the level currently in RAM* plus invent and
migrating chains. The plan's Cluster 2 says "`relink_timers(FALSE)`
after all objs/mons exist," which — applied to a world where every
visited floor has just been hydrated at once — is a different function
with a different result. Get this wrong and the take reintroduces
D-1037 (off-level timers firing) on the restore path, silently.

Second largest: **three of the per-level chunks the plan will rely on
are already broken or absent in the shipping JSON path**, and the plan
does not list them. Traps are the worst — see **M3**. A falsifier run
against a codec that silently drops traps is worse than no falsifier,
because a green run would be read as evidence.

Counts: **6 must-fix**, **9 should-fix**, **7 missing-scope** items, and
**1 process recommendation** for landing "one big take" without
breaking the runbook's evidence contract.

## A. What the plan gets right

Worth stating plainly, because most of it is right and I don't want the
must-fix list to read as a rejection.

- **The thesis is correct and well-argued.** Public scoring is saturated
  (44/44 at D-1693). `seed0013-friday13-save-then-fullmoon-restore`
  genuinely cannot falsify a ledger — I checked its two segments: seg0
  moves are `   L^LlKLLlJLLLKLhhhh,,da #chat\nhFhFhFhFh    nnSy`, seg1
  is an inspection sweep (`i \ ^X ^O + $ ) [ = " ^? : #vanquished
  #conduct Sy`). Neither contains `>` or `<`. The current-level-only
  restore path is the only thing under test today.
- **The "don't ship binary NHFILE" line is the right line.** JSON is
  already the contract in `js/storage.js`, sessions compare screens and
  RNG rather than save bytes, and Constitution §8.4 only requires that
  persistence go through the VFS. Nothing about the oracle needs byte
  compatibility with C.
- **Design decision 4 (identity is `o_id`/`m_id`) is exactly C's
  design** and is the correct answer to the "cannot `JSON.stringify` a
  live graph" problem.
- **Design decision 7 (`linfo` flags ≠ stash bodies) is a real hazard
  correctly identified.** `game.level_info[i]` today is a mixed record
  (`js/do.js:1464–1487`: `flags` alongside `level`, `fmon`, `fobj`,
  `timers`, …) and JSON must not round-trip that shape.
- **Design decision 5 (invent stays a JS Array) is right** and matches
  D-1691.
- **Design decision 6 (ISAAC is not in the save) is right** — segments
  re-`initRng(seed)` (`js/jsmain.js:~204`) and C does not persist RNG
  state either.
- **The scoping is disciplined.** No `sessions/manifest.json` edits,
  cadence stays 44, frozen files untouched, worms/bubbles/exclusions
  named rather than half-done. The `rng-diff` caveat matches runbook §E.
- **Cluster 1's `billobjs` catch is real.** `game.billobjs` is never
  cleared or stashed in `goto_level` — `grep -n billobjs js/do.js`
  returns nothing. Shop bill objects from dlvl 1 currently leak onto
  dlvl 2. C treats `gb.billobjs` as per-level (`save.c:547`, freed by
  `release_data` at `save.c:561`).

## C. Must-fix — these make the oracle wrong, not incomplete

### M1. Relink is per-`getlev`, scoped to one level's object graph

C calls `relink_timers(ghostly)` / `relink_light_sources(ghostly)` at
the **end of every `getlev`** (`restore.c:1299–1300`) — once per level,
while that level is the one in `svl.level` / `fobj` / `fmon`. The one
extra call in `restgamestate` (`restore.c:725–726`) covers the
`RANGE_GLOBAL` sets restored at `:654–655`.

`find_oid` (`shk.c:2777–2804`, JS clone at `js/shk.js:3773`) searches
`invent`, `fobj`, `level.buriedobjlist`, `migrating_objs`, then
`fmon`/`migrating_mons`/`mydogs` minvent. **It never sees another
level.** That is not an accident: it is the invariant that makes the
whole `getlev`-per-level dance work.

The plan's Cluster 2 — "`relink_timers(FALSE)` after all objs/mons
exist" — describes a single global pass over a fully-hydrated
multi-level world. That is a different function. `o_id`s are unique, so
it would not *mis*-bind, but it would bind timers for level *N* while
the game is on level *M*, which is exactly what **M2** then breaks.

**Fix:** `deserLevel(blob)` must relink that blob's timers and lights
against **that blob's own** `fobj` / `buriedobjlist` / `billobjs` /
`fmon[].minvent`, plus the global `invent` / `migrating_objs`. Pass the
search roots in; do not call the global `js/shk.js` `find_oid`. Name
the divergence from C's shared-global `find_oid` in
`docs/c-js-map/turns.md` — it is a deliberate consequence of not
tearing down RAM.

### M2. Other levels' timers and lights must land in the stash, never in `_timer_base` / `light_base`

Follow the C data flow for a non-current ledger on restore:

1. `getlev(nhfp, 0, ltmp)` → `restore_timers(RANGE_LEVEL, elapsed)`
   (`restore.c:1144`) inserts them into `gt.timer_base`, then relinks
   (`:1299`).
2. `restlevelfile(ltmp)` (`restore.c:885`) → `savelev` with
   `WRITING|FREEING` → `save_timers(RANGE_LEVEL)` (`save.c:539`) whose
   `release_data` arm **peels them straight back out**.

Net effect after `dorecover` returns: `gt.timer_base` holds global
timers plus the current level's, and nothing else. Same for
`gl.light_base` (`save.c:540` / `light.c save_light_sources`
`release_data` arm).

Cluster 5 adds `run_timers()` after load (correctly — `restore.c:930`).
If Cluster 3 hydrated other ledgers' timers into the live
`_timer_base`, that `run_timers()` fires hatch/rot/burn/shrink for
objects on floors the hero is not standing on. **That is D-1037
verbatim, on a new path.**

**Fix:** state as a hard invariant in the plan: after
`try_restore_save` returns, `_timer_base` and `light_base` contain
exactly the global set plus the current ledger's. Everything else lives
in `game.level_info[i].timers` / `.lights`, already relinked per M1, in
the same shape `js/do.js:1485` produces today so the existing
`restore_timers(info.timers)` path at `js/do.js:1571` keeps working
unchanged.

Add a cheap assertion to the falsifier: after restore-then-`<`, the
count of `TIMER_OBJECT` entries whose `obj` is not reachable from the
current level is zero.

### M3. Traps are not serialized at all, and restore actively wipes them

This is a live bug in shipping code that the plan inherits without
naming.

`game.ftrap` is **never populated**. Every assignment in the tree either
nulls it (`js/mklev.js:1273`, `js/do.js:1521`) or unlinks from it
(`js/mklev.js:463`, `:11639`, `:11678`, `:11814`). `maketrap` pushes
only to `game.level.traps` (`js/trap.js:967–970`), and `t_at`
(`js/trap.js:975–982`) reads only `game.level.traps`. `js/wizcmds.js:349`
already says so: *"ftrap linked list is often empty (D-0814)."*

Consequences today:

- `js/save.js:281` writes `ftrap: (game.ftrap || []).map(...)` → always
  `[]`.
- `js/save.js:546` does `map.traps = payload.ftrap || []` → **every trap
  on the restored level is deleted.**

`js/bones.js` already fixed its half of this: `:278` writes
`(game.ftrap || lvl?.traps || [])`. `js/save.js` never got the fallback.
That divergence between two copies of the same codec is E1 in
miniature, and it is why E1 is not a stylistic complaint.

seed0013 passes because nothing in its 99 steps observes a trap on the
restored floor. That is precisely the blind spot this take exists to
close, and it means the *first* private falsifier that walks a trapped
floor will fail for a reason that has nothing to do with the ledger —
burning an iteration on a misattributed diagnosis.

**Fix:** the shared level blob serializes `level.traps` (the array).
Decide and name one representation for the codec. Note that the two
representations already coexist in read paths (`js/do.js:1587–1605`
tries `Array.isArray(traps)` then falls back to walking `game.ftrap`
at `:1599`), so `serLevel` fed from a *stash* must not assume `.map`
exists. Also
port C's relative→absolute `trap->dst.dlevel` conversion
(`restore.c:1150–1157`) or name it as a deliberate no-op because JSON
stores absolute.

**Do this first, as its own commit, with its own falsifier.** It is a
correctness fix to the existing save path and it should not be entangled
with the ledger.

### M4. `context.victual.o_id` / `tin.o_id` / `spbook.o_id` / `polearm.m_id` do not exist in JS

Cluster 4 says "null live `victual.piece` / `tin` / `spbook` /
`polearm.hitmon` on save; restore via `o_id` like C." The restore half
has no data to work with yet.

In C these ids are set at **use** time, not save time — `eat.c:412–413`,
`:432`, `:2742–2743`, `:2937–2938`, `:2971–2972`. The assignment inside
`saveobjchn` (`save.c:784–792`) is belt-and-braces, and it *has* to be,
because `Sfo_context_info` is written at `save.c:277`, long before
`saveobjchn(&gi.invent)` at `:301`. An invent victual whose `o_id` were
only captured at save time would be written stale.

`js/eat.js:1924` sets `game.context.victual.piece` and nothing sets
`o_id`. So Cluster 4 has an unlisted prerequisite: port the `o_id` /
`m_id` assignments at every C site first.

There is also a latent **throw** here. `js/save.js:254–257` does
`JSON.parse(JSON.stringify(game.context, fn))`. If `victual.piece` is a
live floor corpse, that serializes the whole `nobj`/`nexthere` chain
behind it; if it is inside a container, `ocontainer` closes a cycle and
`JSON.stringify` raises. Saving mid-meal from a container is not
currently exercised by the public suite. Nulling the pointers on save
fixes both problems, so this belongs in the must-fix tier rather than
"context pointers" prose at the end of Cluster 4.

### M5. Worn slots: drop `invlet` entirely, restore from `owornmask`

`js/save.js:121–128` stores `worn[slot] = obj.invlet`, and
`js/save.js:520–522` rebinds with `findByInvlet`. C does not do this at
all. C walks invent and calls `setworn(otmp, otmp->owornmask)`
(`restore.c:687–692`), then deliberately clears and re-runs
`setuwep` (`:694–697`) so `gu.unweapon` is recomputed.

Three defects, only the first of which the plan names:

- `WORN_SLOTS` is missing `uamul` and `ublindf` (plan catches this).
- Invlet is not a stable identity across restore and cannot express a
  ball/chain that is not in invent — that is what `save_bc` (`save.c:672`)
  / `restore.c:660–672` exist for. The plan defers `save_bc` "loose
  ball" as named, which is fine, but the *mechanism* must still be
  `owornmask`.
- `setuwep` is not re-run, so `unweapon` is not recomputed.

`serObj` already carries `owornmask` through (it copies every scalar
key), and C zeroes `otmp->owornmask` only in the FREEING arm *after*
`saveobj` has written it (`save.c:808`), so the saved value is the live
mask. **Fix:** delete the `worn` payload key, walk restored invent,
`setworn(o, o.owornmask)`, then `setuwep`. Keep reading the legacy
`worn` key only if you care about loading a pre-change save — you
don't, since `vfsDeleteFile` runs on success and no session straddles
the change.

### M6. `elapsed == 0` is a consequence of C's control flow, not a rule to hardcode

The plan's Cluster 5 rule ("`restore_cham` always; catchup and
`hide_monst`/`rnd(10)` only if `elapsed > 0`") reaches the right
behaviour, but the stated reason is wrong, and the wrong reason will
mislead whoever implements the guard.

C's current level is `getlev`'d **twice** — `restore.c:811` at
`REST_GSTATE` and `:898` at `REST_CURRENT_LEVEL`. The guard at
`restore.c:1211` is `if (!u.uz.dlevel || program_state.restoring ==
REST_LEVELS) continue;`. On the **first** pass `u` has not been read yet
(`Sfi_you` is at `restore.c:603`, inside `restgamestate`, which runs
*after* `:811`), so `u.uz.dlevel == 0` and the loop `continue`s before
`restore_cham`. On the second pass `u.uz` is live, `elapsed = svm.moves
- svo.omoves` (`restore.c:1111`) is 0 because `savelev` wrote
`svm.moves` as the level timestamp (`save.c:516`), so `restore_cham`
runs and nothing else does.

So the testable invariant is: **exactly one `restore_cham` per
current-level monster per restore; zero for every other ledger.** Write
that in the plan, and make it the assertion the falsifier checks —
because `restore_cham` *can* consume RNG. `js/mon.js:2645–2659` calls
`normal_shape` when the hero has Protection from Shape Changers or the
monster is `mcan`, and `normal_shape` (`js/mon.js:901–919`) calls
`newcham`. A double `restore_cham` pass would be RNG-visible in exactly
the sessions that matter.

## D. Should-fix

**S1. `savedamage` / `restdamage` is missing from the per-level blob.**
`save.c:549` and `restore.c:1224`. `game.level.damagelist` is live
(`js/shk.js:773–789`, unlinked at `:848–856`). Without it in the codec,
the Cluster 5 preamble `fix_shop_damage` (which the plan wants to
implement, and which exists at `js/shk.js:1076`) has an empty list to
walk and is a no-op. Any shop falsifier is then vacuous.

**S2. `save_stairs` writes `tolev.dlevel` relative.** `save.c:670–680`
subtracts `u.uz.dlevel` when `tolev.dnum == u.uz.dnum`;
`restore.c:972–976` adds it back. A JSON port can legitimately store
absolute — but that must be a **named** decision in the map, not an
omission, because the same relative/absolute dance governs
`trap->dst.dlevel` (M3) and would matter to anyone later porting branch
stairs into the ledger.

**S3. `eshk.bill_p` is a live alias that JSON silently forks.**
`js/shk.js:361` does `eshkp.bill_p = eshkp.bill || null;` and
`js/shk.js:643` reads `eshkp.bill_p || eshkp.bill`. `serMon`'s
`mextra` `JSON.stringify` writes two independent copies; after restore
they are two distinct arrays and a mutation through one is invisible to
the other. Re-alias after deserialising any `ispriest`/`isshk` monster.

**S4. Two save-time mutations in `savemonchn` are unported.**
`save.c:892` `mtmp->mnum = monsndx(mtmp->data)` and `save.c:894`
`forget_temple_entry(mtmp)` for `ispriest`. The second is a real state
change (the priest forgets its temple), observable on a later revisit.
`serMon` does neither.

**S5. `svt.timer_id` is part of the RANGE_GLOBAL timer chunk.**
`timeout.c save_timers` writes it when `range == RANGE_GLOBAL`;
`restore_timers` reads it back. `js/mkobj.js:974` names it omitted
("save/rest timer_id named"). Cluster 4 adds `save_timers(RANGE_GLOBAL)`
but not the counter, so restored timers keep their old `tid` while
`game.timer_id` restarts at 1 — duplicate ids. Only `#timeout` display
ordering depends on it today, but it is one line and it is in the same
C function.

**S6. `place_monster` / `set_residency` / `hideunder` on the JSON
restore path.** `restore.c:1183` `set_residency(mtmp, FALSE)` for
`isshk`, `:1193` `place_monster`, `:1196` `hideunder` for `mundetected`
hiders. `try_restore_save` builds `fmon` and stops. `place_monster`
writes `game._level_monsters` (`js/makemon.js:3247`), which is the JS
analogue of `svl.level.monsters[][]`. `m_at` (`js/mon.js:1234–1252`)
has an `fmon` fallback so this is *mostly* masked — but `level_mon_at`
(`js/worm.js:59–68`) is not, and `set_residency` is not masked at all.
The plan lists this; I am upgrading it from a bullet to a named
should-fix because the masking makes it easy to skip and hard to notice.

**S7. `maxledgerno()` has no home in `js/dungeon.js`.** It exists only
as a private function in `js/o_init.js:84`. C's home is `dungeon.c`.
Cluster 3 needs it; export it from `js/dungeon.js` and have `o_init.js`
import it rather than adding clone #295. Note also the exact bound: C
writes `count = maxledgerno()` then loops `i < count`
(`dungeon.c:172–176`), so index `maxledgerno()` itself is **not**
persisted, even though `ledger_no` returns `1..maxledgerno()`. Reproduce
that or name the difference.

**S8. `dungeon_topology` / `tune` / `inv_pos` are not "should", they are
the same C function.** `save_dungeon` writes, in order: `n_dgns`,
`dungeons[]`, `dungeon_topology`, `tune`, `branches`, `level_info[]`,
`inv_pos`, `mapseenchn` (`dungeon.c:158–187`). `mapseenchn` already
ships (D-1685, `js/dungeon.js:1205`). Adding `linfo` next to it while
leaving `dungeon_topology`/`tune`/`inv_pos` out splits one C function
across two takes for no reason. All three are live on `game`
(`js/dungeon.js:547`, `js/mklev.js:10585–10588`).

**S9. `iflags` should probably not be restored at all.** The plan
correctly flags the merge hazard. My recommendation is stronger: C keeps
`perm_invent` *out* of the save file deliberately (`restore.c:576–580`
comment) and restores `flags` only. `js/save.js:253` writes a whole
`iflags` blob and `:499` merges it over harness options. Since the
segment's `nethackrc` is the authority for DECgraphics / perm_invent /
menu style, restoring saved `iflags` over it can only fight the harness.
Propose: stop persisting `iflags`, and name the specific `iflags` fields
(if any) that genuinely need to survive.

### E1. The bones codec is a third consumer, and it is already a fork

`js/bones.js` carries its own `serObj`, `serMon`, `serObjChain`,
`deserObjChain`, `savecemetery` call sites and level payload
(`js/bones.js:259–294`) — near-duplicates of `js/save.js:43–113` (`serObj` `:43`/`:133`,
`serObjChain` `:68`/`:159`, `serMon` `:78`/`:165`, `deserObjChain`
`:144`/`:313`). They
have already drifted: bones handles `buriedobjlist` as either an array
or a chain (`js/bones.js:274–277`) and `traps` with a `lvl.traps`
fallback (`:278`); `save.js` assumes a chain (`:279`) and has no trap
fallback (`:281`).

Design decision 2 says "one level codec, two consumers." There are
three. Given the standing clone-drift problem in this tree, the plan
should either (a) make `serLevel`/`deserLevel` the single
implementation and have `savebones`/`getbones` call it with a `ghostly`
flag for the `resetobjs` / fruit-negation / pet-untame wrapper — which
is exactly how C factors it, `savelev_core` shared between `savelev`
and `savebones` — or (b) explicitly decline and record the duplication
in `docs/c-js-map/debt.md`. Silently adding a third fork is the one
outcome to avoid.

### E2. `deserLevel` must produce a real `GameMap`

`GameMap` (`js/game.js:31–59`) is a class with an `at(x, y)` method and
a pre-filled `locations[COLNO][ROWNO]`. `try_restore_save` already does
this correctly (`js/save.js:526–545`: `new GameMap()` then overlay). The
plan's Cluster 2 says `deserLevel` "rebuilds stash-shaped record" —
make explicit that the `level` field of that record is
`new GameMap()` + overlay, never a plain object, or every
`game.level.at(...)` caller breaks on a restored non-current floor the
moment the hero climbs to it.

### E3. `omoves` for the current level

C writes `svm.moves` as the current level's timestamp during `savelev`
(`save.c:516`), which is what makes `elapsed == 0` on restore (M6). The
JSON payload has no `omoves` at top level. Add it for symmetry with the
`levels{}` blobs, and set `game.level_info[current].omoves` on restore
so that the *next* `>` then `<` computes elapsed against the right base
